# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

An interactive CPU playground (Vue 3 + TypeScript + Vite) with three architectures, the 8086, RISC-V (RV32IM) and the 6502: the user picks one, builds an instruction word by word, runs it, and watches registers, flags and memory change. A second topic, digital logic, shows the gates behind an operation a CPU just made, a third, number representation, shows what that operation means as unsigned and signed numbers, a fourth, storage, shows the flip-flops that keep the register an instruction wrote, and a fifth, control, shows the decoders that turn a RISC-V instruction's 32 bits into the control lines and the next PC; a topic is a page of its own, and they are linked. The app is called CPU Playground; the repo is still `assembly-app`.

## Commands

```sh
npm run dev          # start the app (vite)
npm run build        # vue-tsc --noEmit && vite build
npm test             # vitest run (tests: src/**/*.test.ts)
npx vitest run src/core/x86/execute.test.ts        # a single test file
npx vitest run -t "some test name"                 # a single test by name
npm run typecheck    # vue-tsc --noEmit
npm run lint         # eslint . (flat config)
npm run format       # prettier --write src
npm run check        # typecheck, lint, format:check and test: the gate before every commit
npm run check:design # no raw colour outside src/ui/styles.css, no hue outside the palette (scripts/claude/check-design-tokens.mjs)
npm run verify:rv32  # RISC-V core vs Capstone and Unicorn (Python: pip install capstone unicorn)
npm run verify:6502  # 6502 core vs py65's assembler and simulator (Python: pip install py65)
```

When a change adds, renames or removes a command (an npm script in `package.json`, or a command developers now run), update this list in the same change. Also update the commands in `README.md`, in both languages.

Style: Prettier with single quotes, semicolons, no trailing commas, 100 columns. Path alias `@` → `src`.

## Architecture

Two layers; keep them separate.

- `src/core/` is the CPU and **must not depend on Vue**. All logic is tested here. It holds one folder per architecture, built on `shared/`, and one for each of the other topics.
  - `shared/`: what every architecture is built on. It never imports an architecture.
    - `architecture.ts`: the `Architecture` interface: an architecture's state, how it executes a program line, where its instruction pointer is in the program (`nextLine` / `setNextLine`), its example programs and its challenges.
    - `program.ts`: a program is a list of instructions; stepping, running (with the step and memory-write limits), and edits (insert, remove, replace, move) that keep jump targets on the right lines.
    - `state.ts`: the CPU state every architecture has (registers by name, flags, memory, I/O ports), snapshots, and memory and port access.
    - `executionRecord.ts`: the **undo record** every architecture extends (history/undo depends on it), with `undo` and `redo`.
    - `challenge.ts`: a `Challenge` (a task, its goals in words, the lines the learner may not use or exceed, and one or more cases: the given lines a program starts with, a test per goal, and an optional `setup` that fills the fresh CPU with other values so a solution cannot borrow a zero from it) and `checkChallenge`, which runs a program **on a fresh CPU** once per case, with that case's given lines, and says which goals and limits it meets. Each architecture lists its own in `challenges.ts`; the test beside it holds a reference solution for every challenge, which must pass in par, and checks that the given lines alone do not.
    - `devices.ts` (the devices behind the ports), `numbers.ts`, `cpuError.ts` (`CpuError`, the error the CPU raises on purpose).
  - `x86/`: the 8086. `architecture.ts` exports `X86`, and `examples.ts` its example programs.
    - `state.ts`: the 8086 registers (8-bit registers are views into AX..DX), FLAGS, 1MB of memory and segment:offset addresses.
    - `instructions.ts`: the instruction set expressed as data; each mnemonic lists its legal operand forms. Adding an instruction starts here.
    - `builder.ts`: given the words chosen so far, computes which operands may come next (drives the UI's word-by-word builder).
    - `execute.ts`: runs one instruction and returns its record, which adds the ALU trace and the interrupt to the shared one. Below it:
      - `executionContext.ts`: what an instruction runs against (reads, writes, flags, ALU, stack, interrupts), recording everything the undo record needs; also the `AluTrace` and the `Handler` type.
      - `handlers.ts`: the table of what every mnemonic does, with the larger handlers in `multiplyDivide.ts` (and the divide error), `shift.ts` and `stringInstructions.ts` (including the `rep` loop).
    - `decode.ts`: what an instruction reads and writes (registers, memory, ports, flags, ALU), including registers it uses without naming them. The diagram and the fetch/decode/execute view are driven by it.
    - `encode.ts`: the 8086 machine code of an instruction, split into fields (prefix, opcode, ModR/M, …), and `assemble` for a whole program. **Display only**; nothing executes these bytes. `encodingFields.ts` builds the fields (ModR/M, immediates, jump distances) and `instructionEncoders.ts` holds the opcode tables and one encoder per kind of instruction.
    - `address.ts` and `flagReasons.ts`: explanations for the UI, worked out from state and the undo record: how segment:offset becomes a 20-bit address, and why each flag got its value.
  - `rv32/`: RISC-V, RV32I with the M extension. `architecture.ts` exports `RV32`.
    - `registers.ts` (x0..x31 and their ABI names), `bits.ts` (32-bit arithmetic: values are kept unsigned with `u32`), `operands.ts`, `instructions.ts` (one form per mnemonic, and its format R/I/S/B/U/J).
    - `state.ts`: the memory map (1MB RAM at 0, the devices at 0x10000000), PC and the line it points at.
    - `execute.ts` runs an instruction, with the operations in `alu.ts` and loads and stores in `memory.ts` (alignment, access faults, devices, and the code read as its machine code).
    - `decode.ts`: rd, rs1, rs2, the immediate, and what each stage will do (ALU inputs, memory access, write back, next PC), for the diagram and the cycle panel.
    - `encode.ts`: the 32-bit word and its fields as bit ranges (`fieldsFor` lays them out from a mnemonic, its registers and its immediate); `disassemble.ts`: a word read back as an instruction, by the encoder's own `OPCODES` and with all of funct7, and its fields (`wordLayout`). **Display only**, as the encoder is; `pseudo.ts`: pseudo-instructions (`li`, `mv`, `j`, `ret`, `beqz`, …) and the real instructions they expand to; `examples.ts`.
    - `pipeline.ts`: how the executed instructions would flow through the five-stage pipeline (IF, ID, EX, MEM, WB), worked out from the history: load-use stalls, stalls until write back when forwarding is off, and the two instructions flushed behind a jump or a branch guessed wrong (both resolved in EX). `branchPredictor.ts` is the guess for a conditional branch: always not taken, always taken, or a one-bit or two-bit state per branch. It follows a history that grows (`startPipeline`, `followPipeline`, `timingOf`), so a step sends one instruction through, and `pipelineTiming` is the same from an empty pipeline. The CPU itself never runs pipelined.
  - `mos6502/`: the MOS 6502 (NMOS). `architecture.ts` exports `MOS6502`.
    - `decode.ts`: the registers, memory and flags an instruction uses, and its mode, size and cycles, for the diagram and the cycle panel.
    - `state.ts` (A, X, Y, SP, PC, the flags in P, and the memory map), `operands.ts` (the 13 addressing modes), `instructions.ts` (the 56 mnemonics with an opcode and a cycle count per mode).
    - `layout.ts`: where each line sits; an instruction is 1 to 3 bytes, so a line's address depends on the lines before it. `encode.ts`: the opcode and operand bytes.
    - `execute.ts` runs an instruction through `executionContext.ts` (reads, writes, the stack, jumps, cycles) and `handlers.ts` (one per mnemonic), with `addressing.ts` (how each mode forms its address, kept as a trace), `alu.ts` (binary and decimal arithmetic) and `memory.ts` (the code, RAM and devices).
  - `logic/`: digital logic, the second topic. It knows no CPU, and imports only itself.
    - `gates.ts`: gates, a circuit as a list of gates in order, `evaluate`, and truth tables. Circuits here are **really evaluated**, never drawn from a CPU's result.
    - `adder.ts` (a ripple-carry adder whose `sub` line inverts B), `shifter.ts` (rows of muxes: a barrel shifter, or one row per count for a CPU that shifts a place at a time).
    - `alu.ts`: an `AluRequest` (add, subtract, AND, OR, XOR or a shift, 8, 16 or 32 bits wide) and `solve`, which builds its circuit, runs it, and names the wires a flag can be read from (`Tap`).
    - `feedback.ts`: `settle`, which runs a circuit whose gates read one another in a loop: every gate takes one step to react, all together, until nothing changes, starting from what the gates held. A circuit that never comes to rest is reported (`settled: false`), not guessed. `evaluate` stays for circuits without a loop. `react` is one such step by itself.
    - `propagation.ts`: a circuit without a loop followed through time: `propagate` gives every wire after each gate delay, from the wires it held when its inputs changed, and the delay each wire is ready at; `atRest` is a circuit whose inputs are all 0, and `depth` the gate delays it has to be given whatever its inputs.
    - `fault.ts`: `Faults` (the broken gates of a circuit, by the signal each drives, and the value its output is stuck at) and `withStuck`, the circuit with those gates reading nothing, so `evaluate` and `propagate` run it unchanged. `solve` takes the faults of an ALU's circuit; a linker never passes any.
    - `nand.ts`: `asNand`, a gate as NAND gates of two inputs, the last driving the gate's own signal (the wires inside are `<id>~1`, `<id>~2`, …; a gate of more inputs is a chain), and `nandCircuit`, a whole circuit built that way. Its test runs the ALU's circuits both ways and compares every wire.
    - `flipFlop.ts`: the memory cells, each built on the one before: the SR latch (two crossed NOR gates), the D latch, and the D flip-flop (two latches on opposite halves of the clock). A cell that has never held a bit cannot settle, so one is started from `holdingBit`.
    - `decoder.ts`: a decoder as two planes of gates (`DecoderShape`: the AND gates that each recognise a pattern of the inputs, and the OR gates they feed), with `solveDecoder`. A pattern no term knows turns its `none` wire on.
    - `programCounter.ts`: a `PcRequest` (the address held, the step and the offset to add, an address computed elsewhere, and the lines `fetched`, `branch`, `taken`, `jump`, `jumpComputed`) and `solvePc`: two adders (`solve`), the gates that choose between their sums, and the counter clocked as a register (`solveRegister`). It is put together from solved parts, not as one circuit, since their wires share names.
    - `register.ts`: a register (a flip-flop per bit behind a switch that feeds it the input or its own output), a `RegisterRequest` (what it holds, what waits at its input, and the mask of the bits that are written) and `solveRegister`, which takes it through one clock cycle and keeps every wire at each moment (`before`, `high`, `after`).
    - `registerFile.ts`: a `RegisterFileRequest` (what every register holds, the value at their shared input, the address, the write line, and whether register 0 is wired to 0) and `solveRegisterFile`: the address decoder (`decoder.ts`: an AND gate per register, none for a wired zero) gives each register its load line, and every register is clocked with it (`solveRegister`). It is put together from solved parts, as the program counter is; registers that go through the same cycle are worked out once.
    - `sequence.ts`: flip-flops on one clock that feed one another, as circuits for `settle`: `shiftRegister` (each flip-flop's input is the output of the one below it, and `in` comes in at bit 0) and `counter` (a bit flips when every bit below it is 1, while `en` is 1). Their test raises and lowers the clock by hand and expects every step to come to rest.
  - `aluLink.ts`, with `x86AluLink.ts`, `rv32AluLink.ts` and `mos6502AluLink.ts`, at the root of `src/core/` because each imports an architecture and `logic/`: the link between the two topics. A linker turns an executed instruction into an `AluCircuit` (the request, the wire behind every flag and whether through a NOT, the flags it always clears) or says why there is none (multiplication, division, decimal mode). Their tests run real instructions and check the circuit against the CPU's result and flags.
  - `representation/`: number representation, the third topic. It knows no CPU, and imports only itself and `shared/`.
    - `readings.ts`: a row of bits on the two scales, unsigned and signed (`wrap`, `signedOf`, `rangeOf`), and every reading of one value (`readValue`: hex, both scales, ASCII, packed decimal).
    - `arithmetic.ts`: a sum or a difference worked out **as whole numbers**, once on each scale: the true answer, what the bits say, and whether it fits. `extension.ts`: a narrow value made wide, by copying its top bit or with zeros. `bcd.ts`: a sum of two packed decimal bytes, digit by digit, with the correction by 6. `bytes.ts`: the bytes of a value as it is written and as it sits in memory in either order, and what a stored value reads as in the other one. `scaling.ts`: a shift worked out as a multiplication or a division by 2 for every place, once on each scale: the true answer rounded down, what was left over, what the bits say, and whether the two agree (a shift left agrees while the answer fits, a shift right on the scale its fill belongs to). `comparison.ts`: two rows of bits compared as whole numbers, once on each scale (`compare`), and whether numbers in that order answer a question such as "less" or "greater or equal" (`holds`).
    - `request.ts`: a `NumberRequest` (one of those, or a value to read) and `solveNumber`.
  - `numberLink.ts`, with `x86NumberLink.ts`, `rv32NumberLink.ts` and `mos6502NumberLink.ts`, at the root of `src/core/` for the same reason: the link into the number topic. A linker turns an executed instruction into a `NumberView` (the request, and for every flag the question about the numbers it answers: a scale, a `Verdict`, and whether the flag works backwards; `comparable` is false where a flag the conditional jumps read is left as it was, as INC and DEC leave the carry) or says why there is none (bitwise logic, rotates, multiplication, division). `shiftReadings` gives the flags of a shift: the carry is a question about the numbers after one place only (the unsigned answer did not fit, or the halving left one over: the verdict `remainder`). Their tests run real instructions and check the numbers against the CPU's result and flags.
  - `registerLink.ts`, with `x86RegisterLink.ts`, `rv32RegisterLink.ts` and `mos6502RegisterLink.ts`, at the root of `src/core/` for the same reason: the link into the storage topic. A linker takes an executed instruction **and the snapshot it left** (the undo record holds only the one before) and gives a `RegisterView`: for every register the instruction wrote, a `RegisterRequest`. The 8086's byte registers are halves of a word register's flip-flops, so a write to AL is a write to AX with half its write lines on. The instruction pointer is left out: it is loaded on every instruction, which the control topic shows (for RISC-V). RISC-V's linker also gives a `RegisterFileView` (`file`: the 32 registers as the instruction found them, their names, and `rd` as the address written), for a write to x0 too, where no register is written; the other two CPUs, whose registers no address field picks, leave it out. Their tests run real instructions and clock the flip-flops of every register, written or not, against the CPU; RISC-V's clocks the whole file too.
  - `controlLink.ts`, with `rv32ControlLink.ts`, `x86ControlLink.ts` and `mos6502ControlLink.ts`, at the root of `src/core/` for the same reason: the link into the control topic. A `ControlView` is the instruction's word and fields, a `ControlShape` (two decoders: the main one reads the opcode, the second reads the main one's wires with funct3 and funct7 and sets the ALU's lines; `solveControl` runs a word through both, with the lines named in its `faults` stuck at a value, which a linker never passes), a `PcRequest`, and a `ControlContext` (the registers the instruction found, its address, whether it was fetched, and memory as it found it). `rv32Control.ts` is RISC-V's shape, its terms built from the encoder's own `OPCODES` so the two cannot disagree. **The control topic is the only place an instruction is decoded from its bits** (these decoders, the datapath they drive, and the disassembler that names a typed word): the CPU itself still runs instructions as data. The linker encodes the instruction at the address it ran from (`encodeAt`), reads its immediate back (`rv32/immediate.ts`), takes "branch taken" and JALR's target from the circuit of `rv32AluLink`, never from the CPU's result, and leaves PC out (`pc: null`) for a branch too far for its immediate. The 8086 (microcode) and the 6502 (a table read on every cycle) return why they have nothing to show. `rv32ControlPath.ts` is the datapath those lines drive: `runDatapath` does a word from its control lines alone (the switches at the ALU's inputs, the circuit of `logic/alu.ts` the ALU's lines call for, the wire a branch reads, memory, what rd takes, and the `PcRequest`), against a `ControlContext`, and gives a `PathOutcome`; what a working control unit never asks for (two values sent to rd, an address nothing worked out) is a `PathConflict`, reported and never guessed (so is a word that is no instruction, which the lines are followed for all the same), and an access that faults, or a jump to an address that is not a multiple of 4, is a `trap`. `rv32ControlMemory.ts` gives the linker the memory an instruction found (`memoryBefore`: what the instruction itself loaded is the value its record kept, and anything else is the CPU's memory with the bytes the instruction wrote put back, read through `load`; a store only says whether it would trap, through `storeFault` of `rv32/memory.ts`).
  - `comparisonTasks.ts` and `comparison.ts`, at the root of `src/core/` because they import every architecture: the same small tasks written for each CPU (with a lesson saying why the programs differ), and `measure`, which runs each program from a fresh CPU and counts its lines, code bytes, instructions run, memory writes and, on the 6502, cycles.
- `src/ui/`: Vue components in `ui/components/`, composables (`use*.ts`) and plain helpers (the other `.ts` files). `App.vue` keeps one CPU per architecture (`useCpu(X86)`, `useCpu(RV32)`, `useCpu(MOS6502)`) and shows the workbench of the one chosen in the header (`X86Workbench.vue`, `Rv32Workbench.vue`, `Mos6502Workbench.vue`), each loaded when first shown (the others are fetched once the page is idle) and kept alive after that, so switching back is instant. A workbench lays out its panels in the shared columns and gives `useWorkbench.ts` its hooks (which programs use the devices, what a step sounds like, the page actions, which `useWorkbenchPage.ts` builds from its `builder` and `memoryView` refs); `useProgramCode.ts` holds its program as text and machine code and what the machine code panel shows; `AppChrome.vue` is the header, palette and dialogs around the panels. Shared panels (`ProgramPanel`, `HistoryLog`, `DevicesPanel`, `InstructionBuilder`) take an architecture's differences as props: a format function, `LineCode` (`programCode.ts`), `DeviceAccess` (`deviceAccess.ts`), and an `InstructionGrammar` (`builderGrammar.ts`; `x86Grammar.ts`, `rv32Grammar.ts`, `mos6502Grammar.ts`). The builder's choices are worked out in `useBuilderOptions.ts` and its arrow keys in `useBuilderArrows.ts`; `BuilderTokenBox.vue`, `BuilderOptions.vue` and `BuilderActions.vue` draw its word box, its options and its buttons. A program line is edited in the builder: a grammar's `parse` turns the line back into words, and `useProgramLines.ts` holds which line is being edited, and keeps the lines locked at the top of the program (a challenge's given lines, counted by `keptGiven` and passed in by `useCpu`) from being edited, moved, removed or pushed down, by the rules of `programLock.ts`; `ProgramLineActions.vue` is a line's buttons and menu. A CPU's program is saved to localStorage and read back through `programStorage.ts`, which drops anything the architecture does not accept. `FlatMemory.vue` (with `flatMemory.ts`) is the memory panel of the flat address spaces, RISC-V's and the 6502's; the 8086's `MemoryView.vue` works out its rows and addresses in `x86MemoryView.ts`, and both colour a recent write with `memoryHeat.ts`. Panels of one architecture are named for it (`Rv32Diagram.vue`, `Mos6502Diagram.vue`, …; the 8086's kept their original names), and their view logic is in plain helpers: RISC-V's in `rv32Explain.ts`, `rv32Datapath.ts`, `rv32View.ts` and `rv32Pipeline.ts` (the pipeline chart, shown by `Rv32Pipeline.vue` in place of the cycle strip, with its switches, forwarding and the branch predictor, drawn by `Rv32PipelineOptions.vue` and held in `useRv32Pipeline.ts`; `useRv32Timing.ts` works the timing out once, a step at a time, for the chart and for the sound of a step alike), the 6502's in `mos6502Explain.ts`, `mos6502Alu.ts` (the ALU's sum and why each flag is set), `mos6502Diagram.ts` and `mos6502View.ts`. The 8086's cycle text is in `x86Explain.ts`, with the condition of each conditional jump in `x86Jumps.ts`; `explainText.ts` holds the words the three explanations share (why a jump was taken or not). `useCpu.ts` wraps an architecture in Vue reactivity, built from `useCpuError.ts` (the error on show), `useCpuHistory.ts` (undo, redo, seek), `useProgramLines.ts` (editing the program), `useProgramRun.ts` (running on a timer) and `usePhaseStepping.ts` (fetch, decode, execute). `useCpuDiagram.ts` works out what the CPU diagram shows, and its parts (`Diagram*.vue`) only draw it. `CpuCanvas.vue` is the CPU panel the three diagrams share: its header, and the flat sheet the chip is drawn on. The sidebar is `SidebarColumn.vue`: the reorderable `SortableColumn` (a panel is dragged by its header, or moved with Alt and the arrows on its `data-sortable-handle` button; `useSortableDrag.ts` and `useSortableKeys.ts`) with each panel wrapped in a `SidebarSection.vue` (collapse, close, and the line that resizes it); the stage is a fixed `StageColumn.vue`, its state in `useSidebarLayout.ts` (what is collapsed and each panel's size, remembered) and `useSidebarResize.ts`, its rules in `sidebarLayout.ts`. A panel marks the list that should take its room with `data-fill`. The layout follows the window's width (`layoutMode.ts`, read through `useLayoutMode.ts`; the style sheets switch at the same 48rem and 64rem): two panes on a desktop, the sidebar as a drawer over the stage on a tablet, and on a phone one of three views (`ViewTabs.vue`: Code, CPU, Memory & I/O). `useWorkbenchView.ts` holds which view or drawer is on show, `PaneFrame.vue` is the two panes of any workbench (with `ViewTabs.vue`, a phone's views of them, and the drawer every page shares), `WorkbenchPanes.vue` is the CPU's three views of them, and `stagePanels.ts` lists the stage's panels and the phone view of each; hidden panels stay mounted. Below a desktop `ResultStrip.vue` (filled by each architecture's `*ChangeStrip.vue`) keeps the last result in sight. `TransportBar.vue` is put together from `TransportRun`, `TransportSpeed`, `TransportHistory` and `TransportPanels`, with `TransportMore` holding what a narrow bar has no room for. The run buttons take their words from `transportLabels.ts`, and `DisabledReason.vue` lets a button that is off say why. `useKeyboardInset.ts` follows a touch screen's on-screen keyboard, and `TapTooltip.vue` is a tooltip a tap opens too. `useCpuReset.ts` decides when a reset asks first, and runs a finished program again. The stack has a panel of its own on the stage, `StackPanel.vue`, which draws a `StackView` (`stackView.ts`: a row per value from the top down, what it is, the instruction that put it there, and what the last instruction pushed or took off). Each architecture reads its own (`x86Stack.ts`: words from SS:SP; `mos6502Stack.ts`: the bytes of page $01, a pushed address as one row; `rv32Stack.ts`: the words from sp to the top of RAM, since no instruction pushes), `stackWriters.ts` keeps which record wrote each byte last, following a history that grows without reading it again, and `useStack.ts` works the view out only while the panel reads it. Whether it is shown is `useStackShown` (`usePanels.ts`), flipped from the transport bar and the palette. Prediction mode asks what an instruction will do before it runs: `prediction.ts` holds a `Question` (whether a branch is taken, the value a register will hold, or the flags of a comparison), the `Answer`, how one is graded and a `Predictor`, an architecture's side of it (`x86Prediction.ts`, `rv32Prediction.ts`, `mos6502Prediction.ts`: the question an instruction deserves, the truth read from its record and the CPU right after it, never from a trial run, and the existing explanation as the reason). `usePrediction.ts` holds the question waiting (the last answer and the run's tally are `usePredictionScore.ts`'s), and gives a workbench its `controls`: the CPU with Step, the last phase, the builder's Run and Run (`usePredictionRun.ts`, a run that waits at each question) going through the question, which is what a workbench hands `useWorkbench` and its transport bar in place of the CPU. `PredictionBar.vue` (with `PredictionAnswer.vue`) is the question and the verdict above the transport bar, with the focus around a question in `usePredictionFocus.ts`; the mode and where it asks are settings of `usePreferences.ts`. `useCommands.ts` builds the Ctrl+K command palette; a workbench adds the commands of its own panels through the `commands` hook of `useWorkbench`. The challenges: `useChallenges.ts` holds whether their list is open, the challenge each CPU is working on and the ones solved (the last two remembered, and read back through `storedRecord.ts`, which trusts nothing in storage), and `ChallengesDialog.vue` is the list, loaded the first time it opens; starting one (`startChallenge` in `useChallenge.ts`, wired in `App.vue`) loads its given lines as an example is loaded. `useChallenge.ts` judges a CPU's program against its challenge whenever the program changes, never on the CPU on show, and leaves the challenge when another program is loaded whole; `ChallengePanel.vue` is the sidebar's `challenge` panel (on show only while there is a challenge: closing it leaves it), with its text in `challengeView.ts`. `CompareDialog.vue` sets the comparison tasks side by side (its rows and text in `comparisonView.ts`); `useComparison.ts` holds whether it is open, so the header and the palette can open it, and it is loaded the first time it opens. Loading a task's program into a CPU (`loadProgram` in `useCpu`) is wired in `App.vue`, which holds the three CPUs. A program is shared as a link: `shareLink.ts` is the link's format (`share=<version>.<architecture>.<payload>` in the address's fragment: the stored program, deflated, in base64url) and reads one back through `parseProgram`, so a link is trusted no more than storage is; `useShare.ts` holds whether `ShareDialog.vue` is open (the header and the palette open it; it is loaded the first time, through `useLazyOpen.ts`, the open state the lazily loaded dialogs share), and `useShareLink.ts` makes the link of the program on show and copies it. `useSharedProgram.ts` reads a link from the address at startup and on `hashchange`, takes it out of the address, and opens its program at once or, when that would replace another program, after `SharedProgramDialog.vue` asked; the loading itself (`loadShared`) is wired in `App.vue`. `FeedbackDialog.vue` is the form to the developer, open from the header of every topic and from the palette: `useFeedback.ts` holds whether it is open, its draft and the sending (a `POST` to `VITE_FEEDBACK_ENDPOINT`; without one a production build offers no feedback and development prints it), and `feedback.ts` what makes a draft sendable and the fields that are sent. `__APP_VERSION__` (a `define` in `vite.config.ts`, declared in `src/env.d.ts`) is the version sent with it. ## Code structure

Every change, new code or an edit to existing code, must leave the structure modular and in line with these rules. If existing code you touch breaks one of them, fix it as part of the change, or tell the user when the fix is too big for the task.

**Layers.** Imports only go downward, never up or sideways into a higher layer:

| Layer       | Files                                               | May import                                                                                                                                       |
| ----------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Components  | `src/ui/components/*.vue`, `src/App.vue`            | everything below, other components, `src/components/ui/` (shadcn)                                                                                |
| Composables | `src/ui/use*.ts`                                    | composables, helpers, core, Vue/VueUse                                                                                                           |
| Helpers     | other `src/ui/*.ts` (`describe.ts`, `sounds.ts`, …) | helpers, core. **No Vue**: plain functions over plain data                                                                                       |
| Core        | `src/core/**/*.ts`                                  | core only: `shared/` only itself, an architecture folder, `logic/` or `representation/` only itself and `shared/`; the files at the root of `src/core/` any of them |

ESLint enforces the import rules of the core, helper and composable layers, and the 500-line file limit below; `npm run lint` fails on a violation. The other rules here are on you.

- **Anything reactive is a composable:** code that holds `ref` / `computed` / `watch` state or uses VueUse lives in a `use*.ts` file and is named `useX`. A helper never imports Vue.
- **Components wire, they don't compute:** a `.vue` file binds state to markup. Calculations, decisions and text formatting go in a helper or composable, where they can be unit-tested. If a function in `<script setup>` would deserve a test, it belongs in a `.ts` file.
- **Shared types live in `.ts` files:** never import a type from a `.vue` file. A component may import its prop types from a `.ts` file, not the other way around.
- **No import cycles** between files.

**Size and responsibility.**

- **One responsibility per file:** you should be able to say what a file does in one sentence without "and". The name says what it is: `useX` for a composable, a noun for a helper or a core module, PascalCase for a component.
- **File size** (source files, not tests): past **~300 lines**, check before adding to it whether it now holds more than one responsibility. Past **~500 lines** it must be split: split it before adding more. A component counts its template too; split a large template into child components.
- **Function size:** about **50 lines** at most; split a longer function into named steps. Two things are not "long functions": a composable factory (`useX`), whose inner functions follow the limit but whose body past ~150 lines should be split into smaller composables or helpers; and a flat list of data (the instruction table, the palette's command list) whose entries are short.
- **Tests** live next to their module (`x.test.ts` for `x.ts`) and are exempt from the size limits; group them with `describe`.

**Adding and changing code.**

- **Put new code where it belongs:** first look for the existing file whose responsibility it is, in the right layer. Create a new file only when no file fits, and give it a name that says its job.
- **Don't duplicate:** the third copy of the same logic is the moment to extract a shared function. Don't add abstractions for a single use.
- **Exports are the module's API:** export only what other files (including tests) use, plus types that appear in exported signatures. Remove exports nobody uses.
- **Before finishing a task** that added a file or grew one noticeably, re-check it against this section.

## Verification

A change is checked in two tiers: deterministic gates first, review agents only where a gate cannot judge.

- **While editing (hooks, `.claude/settings.json`):** after every Edit or Write, ESLint and Prettier check that one file (`scripts/claude/post-edit.mjs`). When a turn ends with uncommitted changes under `src` or `scripts`, the Stop hook runs the typecheck and `vitest --changed` (`stop-check.mjs`); it blocks the stop once at most. `git-guard.mjs` denies `--no-verify`, a force-push and deleting a remote branch, and asks before a commit on `main`; `pre-edit.mjs` asks before a hand edit in `src/components/ui`.
- **`/verify` (`.claude/commands/verify.md`) is the one entry point before a commit.** `scripts/claude/route.mjs` reads the diff against `main` and decides what runs. Tier 1 always runs: `npm run check`, plus `check:design` for components and style sheets, `verify:rv32` / `verify:6502` with one fresh seed when that core or `shared/` changed, and `build` when a dependency or the build configuration changed. Tier 2 runs when simulator code changed or more than 30 lines of UI did, and only the agents whose files changed: `isa-correctness`, `vue-architecture`, `design-responsive`, `a11y-interaction`, `perf-runtime` (`.claude/agents/`). `/verify --full` runs all five on any code change. A change to documentation, tests or generated components alone runs no agent.
- **Agents report, they never edit.** Each answers `PASS | WARN | BLOCK` with findings as `path:line`, a severity (Blocker, Warning, Nit), evidence and a fix. `/verify` merges them, confirms every Blocker in the code, fixes what is mechanical, and stops after two fix rounds. A fix to what an instruction does, to the undo record or to an encoding is never automatic.
- **Changing the rules:** the routing lives in `route.mjs` and is tested in `route.test.mjs`; change both together. A colour that was in the code before a rule of `check:design` existed is listed under `KNOWN` in the script: delete its entry when it moves to a token of the palette. The palette itself (which hues a token may hold) is in `designPalette.mjs`, tested in `designPalette.test.mjs`; the `chart-*` tokens are the one exception, allowed in the encoding panels only.

## Execution model (non-obvious)

- Instructions **run as data, not as bytes**. On the 8086, IP is the index of the next program line (L0, L1, …); jump/call targets are lines. CALL pushes the next line onto the stack and RET pops it. The machine code from `encode.ts` is shown beside the program but never executed, and it is not written into memory.
- Shared code never reads an instruction pointer itself: it asks the architecture for `nextLine` and moves it with `setNextLine`. Each architecture decides how its instruction pointer maps to a program line (the 8086's IP simply is the line).
- On RISC-V, PC is a real byte address: line n is at 4n, so links (`jal`), `auipc` and `jalr` targets are real addresses. A jump to an address that is not the start of a line is a `CpuError`. The code is readable as memory (its encoding) but a store into it is a `CpuError`: the program cannot modify itself. Pseudo-instructions are expanded into real lines when added, so the program only holds real instructions.
- On the 6502, PC is a real address too, but instructions are 1 to 3 bytes, so a line's address comes from the layout of the lines before it (`layout.ts`). The code starts at $0600, the devices sit at $D000 + port, the stack is page $01, and the BRK vector is at $FFFE. BRK is encoded with its signature byte (two bytes, `00 00`), so RTI returns to the next line. JMP and JSR only take a program line, never a numeric address. Decimal mode follows the NMOS chip, N, V and Z included.
- A label used as a value (`mov word [0x84], L8`) is the **line number** at run time, while `encode.ts` shows it as the byte offset of that line. Keep both in mind when touching either side.
- A share link carries an architecture and its program, nothing of the CPU's state. Its payload is the serialized program, so a change to an instruction's shape breaks old links (they are refused, never half-read): raise the link's version and convert the old one.
- An instruction runs immediately (Enter) or is appended to the program (Shift+Enter).
- Memory operands are `byte`/`word` `[bx]`, `[si]`, `[di]`, `[bp]` or `[offset]`. `[bp]` uses SS; all others use DS.
- Shift counts are `1` or `CL`, as on the 8086.
- String instructions read DS:SI and write ES:DI. A `rep`/`repe`/`repne` repetition runs to the end as **one step** with one undo record.
- Interrupts go through the vector table at `0000:n×4`, where the offset word holds a handler's line number. An **empty vector is a `CpuError`** rather than a jump to line 0, so L0 cannot be a handler. A divide error enters INT 0 only if that vector is installed.
- I/O ports are separate from memory, with separate input and output bytes per port. Output port writes are part of the undo record (`portWrites`); the input ports are set by the devices panel and survive Reset.

## Git

- **Atomic commits:** one logical change per commit. Don't mix a refactor, a bug fix and a feature in one commit, and don't bundle unrelated files. Each commit should leave `npm run check` passing (typecheck, lint, format check and tests; the deploy runs the same four). Stage selectively (`git add -p` or by path), never `git add -A` blindly.
- **Tests with code:** a change to `src/core/` goes in the same commit as its test update.
- **Message format:** `<type>: <description>`, all lowercase, imperative or short noun phrase, no trailing period, subject ≤ 72 characters. Types used in this repo's history: `create`, `update`, `change`, `fix`, `remove`, `init`. Use `create` for new files/features, `update` for extending existing ones, `change` for behavior or design changes, `fix` for bugs, `remove` for deletions.
  - Example: `fix: asHigh bits methods in the Mask class`
- Add a body (blank line after the subject) only when the _why_ isn't obvious from the diff.
- **Branches: one branch per feature.** Every feature, fix or other self-contained task lives on its own branch, to keep history uncluttered.
  - Naming: `feature/<short-name>` for features and changes, `fix/<short-name>` for bug fixes. Lowercase, hyphen-separated, English.
  - Never commit directly to `main`, unless the user explicitly says to.
  - Start each new task from an up-to-date `main` (or from the branch it depends on, if the user says so). If the current branch is a finished, unrelated feature branch, switch to `main` and branch from there instead of piling the new work onto it.
  - Continue on the current branch only when the task is a continuation of that branch's feature.
  - Don't mix two features on one branch. If unrelated work shows up mid-task, finish or commit the current one first.
- **End-of-task Git workflow:** when a task is **fully completed**, do the Git work without waiting to be asked:
  1. Make sure you are on the right branch (create it per the rules above if the task is new).
  2. Run `/verify` (see "Verification"): `npm run check` and the other gates always, the review agents when the change calls for them. Fix failures first; do not commit on a BLOCK.
  3. Split the changes into atomic commits per the rules above and commit them.
  4. Verify `git status` is clean and report the branch and commits to the user, **in Hebrew** (see "Language with the user").
  - **Partial work is exempt:** if the task is only partly done (blocked, failing, waiting for a user decision, or the user stopped midway), do **not** commit or create a branch. Leave the changes uncommitted and say what remains.
  - Do not commit unrelated pre-existing changes the user left in the tree; stage only files that belong to this task.
- **Still needs an explicit request:** merging into `main`, amending, and rewriting history (rebase, `reset --hard`, force-push). Prefer a new commit over amending. A `git push` also needs a request, except the push that follows a merge (next rule).
- **After a merge, push and clean up:** when you merge a branch into `main` (only when the user asked for the merge), finish the job without asking again:
  1. On the merged `main`, run `npm run typecheck`, `npm run lint` and `npm test`. If anything fails, stop: do not push and do not delete the branch; report it.
  2. `git push origin main`. Never force-push. If the push is rejected or fails, stop, keep the branch, and report why.
  3. Only after the push succeeded, delete the branch **locally only**, with `git branch -d <branch>` (the safe form, which refuses an unmerged branch; never `-D`).
  4. **Never delete the branch on the remote (GitHub)**: no `git push origin --delete <branch>` and no `git push origin :<branch>`, even if the branch exists there and even though it is merged. Remote branches are removed only when the user explicitly asks.
  5. Report in Hebrew what was merged, pushed and deleted locally, and mention if a copy of the branch is still on the remote.
  - This applies only to a merge that Claude performs. Pushing a branch that is not being merged still needs an explicit request.
- **After every push to `main`, verify the deploy:** the `deploy` workflow (`.github/workflows/deploy.yml`: lint, format check, tests, build, then GitHub Pages) runs on each push to `main`; pushing another branch triggers nothing. Don't report the work as done until you have seen it finish, using the GitHub CLI (`gh`; if it is missing from PATH, use `C:\Program Files\GitHub CLI\gh.exe`).
  1. Find the run for the pushed commit: `gh run list --workflow deploy.yml --branch main --limit 1` (check that its commit is the one just pushed), then wait with `gh run watch <id> --exit-status`.
  2. On success, check the live site: `https://moti-oren.github.io/assembly-app/` must answer 200 and its `index.html` must reference `/assembly-app/assets/…`, not `/src/main.ts`. Then report in Hebrew that the build and the deploy succeeded.
  3. On failure, read the log (`gh run view <id> --log-failed`), find the cause, and reproduce it locally with the same command the workflow ran (`npm run lint`, `npm run format:check`, `npm test`, `npm run build`).
  4. Fix it on a new `fix/<short-name>` branch from `main`, following all the rules above (atomic commit, `typecheck` / `lint` / `test` passing). The user has authorized this one loop to complete without asking again: merge the fix into `main`, run the same checks, push, and verify the new run the same way.
  5. Stop and report to the user in Hebrew, without trying a fix, when: the failure is not in the code (a GitHub outage, a missing permission, the Pages setting, a secret, a protected environment); the fix would change a workflow's permissions, a repository setting, or the build in a way that is more than a small repair; or two fix attempts in a row did not make the run pass. Never force-push, never delete a remote branch, and don't change repository settings with `gh api` on your own.
  6. If `gh` is not logged in (`gh auth status` fails), say so and ask the user to run `gh auth login`; don't try to work around it.
- **Language of the commits themselves:** the text stored in git (commit subjects and bodies, branch names, code and code comments) is in English.
- **Destructive commands:** before `git reset`, `git checkout -- <path>`, `git clean` or `git stash drop`, inspect what will be lost (`git status`, `git diff`). Uncommitted work may be the user's.
- **Large moves:** commit deletions, moves/renames and new content separately, so `git log --follow` and blame keep working.
- **Lockfile:** `package-lock.json` changes go in the same commit as the `package.json` change that caused them.
- If a change breaks the serialized shape of core state or the undo record, say so in the commit body (`BREAKING:` line).
- Never skip hooks (`--no-verify`). If a hook fails, fix the cause.
- Don't commit `dist/` or `node_modules/` (check `.gitignore` before staging).

## Conventions

- **Adding an instruction** (to the 8086, in `src/core/x86/`): define it in `instructions.ts`, implement it in `execute.ts`, then add tests in `execute.test.ts`. If it touches flags, test the flags too. Then give it an encoding in `encode.ts` (it throws for a mnemonic it does not know, and a test encodes every example program), and list any registers it uses implicitly in `decode.ts`.
- **Undo is a contract:** every path in `execute.ts` must return a complete undo record (registers, flags, memory writes, port writes and IP). A new path without one breaks history.
- **RISC-V is checked against real tools:** after changing anything in `src/core/rv32/` that encodes or executes, run `npm run verify:rv32` (Capstone reads the encodings back, Unicorn runs random programs from their bytes) and a few seeds (`npm run verify:rv32 -- 7`). It needs Python with `capstone` and `unicorn`. LLVM's `clang` is installed but blocked by Windows Application Control on this machine, so it cannot be used.
- **The 6502 is checked against py65:** after changing anything in `src/core/mos6502/` that encodes or executes, run `npm run verify:6502` and a few seeds. It compares registers, flags, memory and cycle counts. Two known py65 differences are handled in the script, not in the core: its cycle table has DEC absolute ($CE) at 3 cycles (the data sheet says 6), and its decimal mode does not reproduce the NMOS N, V and Z, so BCD sums are compared on A and C only.
- **Encodings follow NASM:** where the 8086 allows two encodings of one instruction, `encode.ts` produces the one NASM picks (checked against NASM 3.02 with `bits 16` / `cpu 8086`). Two deliberate exceptions: `int 3` is the one-byte `CC`, and a conditional jump out of short range is reported as a problem instead of being rewritten as an inverted jump over a `jmp`.
- **Typed arrays are not reactive:** memory and port bytes live in `Uint8Array`s, so the UI depends on `memoryVersion` / `ioVersion`. Bump them on every write path.
- **8086 fidelity:** flag behavior (AF, OF, CF, etc.) follows real 8086 semantics, not whatever is convenient. When unsure, check the 8086 reference instead of guessing.
- **UI changes:** `typecheck` and `test` do not cover the UI. Verify it in the browser via `npm run dev` before reporting it done.
- **A topic's circuit is checked against the CPUs:** after changing `src/core/logic/` or a linker (`*AluLink.ts`), run its tests: they execute random instructions on the real cores and compare the circuit's result and every flag. A new operation in a linker needs a case there. Never make a circuit agree by reading the CPU's result into it. The same holds for `src/core/representation/` and the number linkers (`*NumberLink.ts`): the numbers are worked out as whole numbers and compared with the CPU, never read from it. In decimal mode they are compared on A and C only, as `verify:6502` does. The jumps of the number topic (`numbersConditions.ts`) are checked both ways: against the whole numbers for every pair of bytes, and against the real cores, which run a comparison and the jump after it. A register linker (`*RegisterLink.ts`) is checked the other way round, since what is written is the CPU's own value: its test clocks the flip-flops of **every** register, with the write lines off for the ones the instruction did not write, and each must end up holding what the CPU holds. The control linker (`rv32ControlLink.ts`) is checked against the CPU's own decoding: its test runs every mnemonic, fetched from a program and by itself, and compares the main decoder's lines with `decode()`, the ALU decoder's lines with the request of `rv32AluLink`, and the clocked PC with the CPU's. A new instruction needs a term in `rv32Control.ts`. The datapath (`rv32ControlPath.ts`) is checked the same way: for every mnemonic the lines alone must leave the registers, the memory access, the ALU's request and PC as the CPU left them, with no conflict and no trap. A new control line needs its switch there.
- **One page per topic:** a topic has its own workbench component and its own palette commands, inside the shared `HeaderShell`. A link between topics carries what the other topic needs as plain data from the core (as `AluLink`, `NumberLink`, `RegisterLink` and `ControlLink` do), never a component's state. A new topic gets its own linkers and its own call of `useCpuMoment`; the moment, `TopicOrigin` and `TopicLinkButton` are shared.
- **One workbench per architecture:** a panel that shows one architecture's concepts belongs to it (`Rv32*.vue`, helpers `rv32*.ts`) and is wired in that architecture's workbench. A panel both share takes the differences as props; never branch on the architecture inside a shared component.
- **Command palette (Ctrl+K) stays in sync:** the app's command palette lists what the user can do (program, history, devices, run speed, examples, preferences). Its commands are built in `src/ui/useCommands.ts` and shown by `CommandPalette.vue`. Whenever a change adds a user-facing action (a new toggle, panel, preference, run option, or anything the user could reasonably look for in the palette), add the matching command in the same change; when an action is renamed or removed, update or remove its command. Toggles use a label that reflects the current state (`Show …` / `Hide …`). Not every control belongs there; skip purely internal or purely contextual ones. A command that moves focus or scrolls the page must set `moves: 'focus' | 'scroll'`: the open palette locks scrolling and hands focus back on close, which would undo it.
- **README on UI changes:** whenever the UI changes (new or changed controls, shortcuts, panels, behavior the user sees), check whether `README.md` should change too (commands, layout, model, usage). If so, update it in the same change.
- **README is bilingual:** `README.md` has the full guide in English at the top and the same guide in Hebrew (RTL) at the bottom. Any README edit must be applied to both halves so they stay equivalent.
- **shadcn components:** add them with `npx shadcn-vue add <name>`, never by hand-writing files in `src/components/ui/`.
- **`cn` is intentional:** the `cn` package is shadcn's replacement for `clsx` + `tailwind-merge`. The generated components import it directly and `src/lib/utils.ts` re-exports it. Don't remove it or swap in `clsx`/`tailwind-merge`.
- **Dependencies:** don't add new packages without asking.
- **Comments:** only where the _why_ is not obvious. No comments that restate what the line does.
- **Language with the user:** everything addressed to the user is in Hebrew: replies, explanations, questions and all git reports (which branch was created, which commits were made, what each one contains, what was skipped and why). Only the artifacts stay in English: code, comments, commit messages and branch names. When quoting a commit message or branch name in a Hebrew report, keep it verbatim in English and write the surrounding explanation in Hebrew.
